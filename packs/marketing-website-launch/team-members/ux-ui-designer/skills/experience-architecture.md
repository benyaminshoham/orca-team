# Experience architecture

## Purpose

Design a coherent site structure and page/interaction model around priority user journeys and content truth.

## Triggers

Use for site discovery, sitemap and navigation, page templates, journey design, form flow, migration restructuring, or scope change.

## Required inputs

Approved brief; audience needs and journeys; message architecture; content inventory; required pages; brand constraints; analytics/search inputs; technical limits; current URLs for migrations.

## Workflow

1. Map audience tasks, entry points, decisions, questions, failure paths, and next steps.
2. Inventory content and classify keep, revise, combine, create, redirect, archive, or unresolved without changing URL decisions unilaterally.
3. Define a sitemap and navigation model with clear labels, predictable grouping, page purposes, and multiple finding paths when needed.
4. Select a small set of page and module patterns based on repeated content intent, not visual novelty.
5. Create low-fidelity flows and wireframes using real or bounded representative content. Show hierarchy, headings, landmarks, actions, proof, disclosure, and recovery.
6. Model forms and interactions end to end, including instructions, validation timing, errors, confirmation, consent, abandonment, and unavailable states.
7. Test the architecture against priority journeys, long/short content, narrow viewports, keyboard order, localization expansion, and migration continuity.
8. Record decisions, unresolved content/technical dependencies, and acceptance criteria.

## Decision rules

- Information architecture follows user meaning and business priority, not internal org charts alone.
- Navigation labels must be distinguishable and understandable without relying on hover.
- Reuse a pattern only when semantics and behavior are genuinely the same.
- Forms ask only for approved necessary data and permit understandable correction.
- Do not use layout order that conflicts with reading or focus order.

## Output contract

Journey map; content disposition input; sitemap/navigation model; page/template inventory; wireframes; interaction and form flows; state inventory; rationale, dependencies, and acceptance criteria.

## Quality checklist

Priority tasks have complete paths; each page has purpose; navigation is coherent; content hierarchy matches meaning; edge/failure states exist; responsive and assistive access are feasible.

## Failure and escalation conditions

Escalate conflicting page purposes, missing decision owner, incomplete content inventory, unresolvable migration/URL conflict, data collection without approved purpose, or journeys requiring product scope outside the pack.

## Collaboration touchpoints

Strategist owns content intent and wording; engineer challenges feasibility; reviewer challenges testability and accessibility; PM accepts handoffs and routes decisions.
